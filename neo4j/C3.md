# C3 — Debug de Cypher

Todos os trechos rodaram no meu grafo via `cypher-shell`. A partir do (ii), cada execução foi feita com `timeout 30`, que mata o processo se passar de 30 s. O `tempo_total_s` das saídas inclui ~1,5 s só pra JVM do `cypher-shell` subir.

## (i) CREATE duplicando nós

```cypher
CREATE (a:Empresa {cnpj:'E1'})-[:SOCIA_DE {pct:30}]->(b:Empresa {cnpj:'E2'})
```
**Sintoma:** em vez de ligar a E1 e a E2 que já existem, aparecem uma E1 e uma E2 novas, sem `nome` e sem `sancionada`, ligadas entre si. As originais continuam sem a aresta.

**Causa raiz:** o `CREATE` sempre cria tudo o que está no padrão, nós e relação. Ele não procura nada antes. E o banco não tinha nenhuma constraint de unicidade em `cnpj` pra impedir isso.

**Evidência antes** ([c3_i_antes_saida.txt](c3_i_antes_saida.txt)):

| | antes do CREATE | depois do CREATE |
|---|---|---|
| nós `E1` | 1 | **2** |
| nós `E2` | 1 | **2** |
| total de `:Empresa` | 30 | **32** |
| arestas E1→E2 (entre as originais) | 0 | 0 |

**Limpeza dos duplicados** (os duplicados são os únicos sem `nome`):
```cypher
MATCH (e:Empresa) WHERE e.cnpj IN ['E1', 'E2'] AND e.nome IS NULL
DETACH DELETE e
```
→ `duplicados_apagados: 2`.

**Código corrigido:**
```cypher
MATCH (a:Empresa {cnpj: 'E1'}), (b:Empresa {cnpj: 'E2'})
MERGE (a)-[r:SOCIA_DE]->(b)
ON CREATE SET r.pct = 30
```
O `MATCH` encontra os nós que já existem, e o `MERGE` só cria a relação se ela ainda não existir. Coloquei o `pct` no `ON CREATE SET` e não dentro do padrão do `MERGE` porque, se no futuro o pct mudar, um `MERGE {pct:40}` criaria uma segunda aresta em vez de reconhecer a que já existe.

Também criei uma trava no banco:
```cypher
CREATE CONSTRAINT empresa_cnpj_unico IF NOT EXISTS FOR (e:Empresa) REQUIRE e.cnpj IS UNIQUE
```

**Evidência depois** ([c3_i_correcao_saida.txt](c3_i_correcao_saida.txt), [c3_i_constraint_saida.txt](c3_i_constraint_saida.txt)):

| | depois da correção |
|---|---|
| nós `E1` / `E2` | 1 / 1 |
| total de `:Empresa` | 30 |
| arestas E1→E2 | 1 (pct 30). Rodei o MERGE **duas vezes** e continuou 1 |
| `CREATE` original de novo | **bloqueado**: `Node(6) already exists with label Empresa and property cnpj = 'E1'` |

## (ii) Caminho sem limite e sem direção

```cypher
MATCH (s:Empresa {sancionada:true})-[:SOCIA_DE*]-(x:Empresa) RETURN x.nome
```
**Sintoma:** sem limite, a consulta tende a nunca terminar e a consumir memória. Reproduzi só com `LIMIT 20` e `timeout 30` ([c3_ii_antes_saida.txt](c3_ii_antes_saida.txt)). Com o LIMIT ela termina rápido (o LIMIT para a enumeração cedo), mas o resultado já mostra o problema:
- **nomes repetidos** (Empresa 12, 18 e 29 aparecem duas vezes cada), porque cada caminho diferente vira uma linha;
- empresas que **não têm relação de controle** com a E22 (Empresa 1, 0, 6, 9…), porque sem direção a consulta sobe e desce pela rede.

**Causa raiz:** `*` sem limite enumera **todos os caminhos** de qualquer tamanho, e sem direção cada aresta pode ser percorrida nos dois sentidos. O número de caminhos cresce exponencialmente com o tamanho. Medi no meu grafo, contando os caminhos sem direção a partir da E22 por tamanho ([c3_ii_crescimento_saida.txt](c3_ii_crescimento_saida.txt)):

| tamanho | caminhos | empresas distintas |
|---|---|---|
| 1 | 2 | 2 |
| 2 | 7 | 7 |
| 3 | 19 | 12 |
| 4 | 59 | 25 |
| 5 | 142 | 28 |
| 6 | 338 | 29 |
| 7 | 801 | 29 |
| 8 | 1.770 | 29 |

A partir do tamanho 6, as empresas distintas param em 29 (o grafo todo), mas os caminhos continuam crescendo ~2,3× a cada nível. É trabalho desperdiçado que só repete as mesmas empresas. Com 46 arestas, os caminhos podem chegar a dezenas de arestas de comprimento, e aí a conta explode.

**Código corrigido:**
```cypher
MATCH (s:Empresa {sancionada: true})-[:SOCIA_DE*1..3]->(x:Empresa)
WHERE x <> s
RETURN DISTINCT x.nome AS empresa
```
**Evidência depois** ([c3_ii_correcao_saida.txt](c3_ii_correcao_saida.txt)): **11 empresas, sem repetição** (as mesmas da C2), percorrendo só **13 caminhos**.

## (iii) Pilha com direção invertida e id literal

```cypher
MATCH (base:Container {id:'BASE_DA_PILHA'})-[:EMPILHADO_SOBRE*1..3]->(x:Container) RETURN x.id
```
**Sintoma:** devolve 0 linhas.

**Causa raiz, que são duas:**
1. `'BASE_DA_PILHA'` é o **nome do parâmetro**, não o id. Nenhum container tem esse id (`nos_com_id_literal: 0`). O meu é **`K28`**.
2. A direção está invertida. `(a)-[:EMPILHADO_SOBRE]->(b)` quer dizer que a está **em cima** de b. Quem está preso em cima da base **aponta para ela**. Saindo da base com `->` a consulta procura o que está *embaixo* da base, e embaixo da base não tem nada.

**Evidência antes** ([c3_iii_antes_saida.txt](c3_iii_antes_saida.txt)):

| variação | linhas |
|---|---|
| original (`'BASE_DA_PILHA'`, `->` saindo da base) | 0 |
| só trocando o id pra `K28` (direção ainda errada) | **0** |

Ou seja, só trocar o id não resolve.

**Código corrigido:**
```cypher
MATCH p = (x:Container)-[:EMPILHADO_SOBRE*1..3]->(base:Container {id: 'K28'})
RETURN x.id AS container_acima, length(p) AS niveis_acima
ORDER BY niveis_acima
```
**Evidência depois** ([c3_iii_correcao_saida.txt](c3_iii_correcao_saida.txt)):

| container_acima | níveis acima da K28 |
|---|---|
| K29 | 1 |
| K30 | 2 |
| K31 | 3 |

Faz sentido pelo gerador: a pilha é K28 ← K29 ← K30 ← K31 (`topo: K(4s+n)`, `base: K(4s+n-1)`, com s = 7).

## (iv) Contagem sem DISTINCT

```cypher
MATCH (k:Container)-[:PASSOU_POR]->(t:Terminal) WHERE k.classe='Perigoso' RETURN t.nome, count(k)
```
**Sintoma:** os números de "containers perigosos por terminal" vêm inflados.

**Causa raiz:** o `MATCH` gera **uma linha por relação `PASSOU_POR`**, não uma por container. Se o mesmo container passou duas vezes pelo mesmo terminal, ele aparece em duas linhas e o `count(k)` conta duas vezes. No meu grafo isso acontece com 4 containers ([c3_iv_antes_saida.txt](c3_iv_antes_saida.txt)): K1 no T1, K61 e K89 no T2, K86 no T5.

**Código corrigido:**
```cypher
MATCH (k:Container)-[:PASSOU_POR]->(t:Terminal)
WHERE k.classe = 'Perigoso'
RETURN t.nome AS terminal, count(DISTINCT k) AS containers_perigosos
ORDER BY terminal
```
**Evidência antes/depois** ([c3_iv_correcao_saida.txt](c3_iv_correcao_saida.txt)):

| terminal | `count(k)` (original) | `count(DISTINCT k)` (corrigido) |
|---|---|---|
| T1 | 11 | **10** (K1 2×) |
| T2 | 17 | **15** (K61 e K89 2×) |
| T3 | 9 | 9 |
| T4 | 13 | 13 |
| T5 | 6 | **5** (K86 2×) |

A diferença é exatamente o número de passagens repetidas que achei antes.
