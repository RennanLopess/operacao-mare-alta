# B2 — Debug do pipeline

Objetivo: no período todo, classe `Refrigerado`, top 3 terminais por peso total.
Script: [b2.js](b2.js) · saída: [b2_saida.txt](b2_saida.txt) · explains: [original](b2_a_original_explain.json), [corrigido](b2_c_corrigido_explain.json)

## a) Rodando como está

```js
db.movimentacoes.aggregate([
  { $project: { terminal: 1, classe: 1 } },
  { $group: { _id: { terminal: "$terminal", classe: "$classe" }, kg_total: { $sum: "peso_kg" }, mov: { $sum: 1 } } },
  { $limit: 3 },
  { $sort: { kg_total: -1 } },
  { $match: { "_id.classe": "Refrigerado" } }
])
```
Rodei 3 vezes seguidas, sem mudar nada:
```
execução 1: []
execução 2: []
execução 3: [{"_id":{"terminal":"T5","classe":"Refrigerado"},"kg_total":0,"mov":19909},
             {"_id":{"terminal":"T1","classe":"Refrigerado"},"kg_total":0,"mov":20047}]
```
Numa das vezes o `$limit 3` pegou `T2/Geral`, `T4/Perigoso` e `T2/Granel`, e nenhum é Refrigerado, então o `$match` no fim deixou tudo vazio. **A resposta é errada e ainda muda a cada execução.** Explain: `COLLSCAN` com 400.000 docs, `group` gerando 20 grupos, `$limit(3) > $match(1) > $sort(1)`.

## b) Defeitos

| # | defeito | tipo | evidência |
|---|---|---|---|
| 1 | `$sum: "peso_kg"` **sem `$`**: soma a string literal "peso_kg" e não o campo. O `$sum` ignora o que não é número, então dá 0. | lógica | `{$sum:"peso_kg"}` = **0**, e `{$sum:"$peso_kg"}` = 6.394.785.318 na coleção inteira |
| 2 | `$project {terminal, classe}` **descarta `peso_kg`**: mesmo com o `$`, o campo não existe mais quando chega no `$group`. | lógica | `$project` + `$sum:"$peso_kg"` = **0** |
| 3 | **`$limit` antes do `$sort`**: pega 3 grupos quaisquer (a ordem de saída do `$group` não é garantida) e só depois ordena. Não é um "top 3". | lógica | o resultado mudou entre execuções |
| 4 | **`$match` no fim**: filtra a classe depois de agrupar e limitar, então pode sobrar 0 resultado. | lógica | execuções 1 e 2 vazias |
| 5 | O mesmo `$match` no fim, visto pelo desempenho: **sem filtro no início, não usa índice** e lê a coleção toda pra depois jogar fora 3/4. | desempenho | COLLSCAN, 400.000 docs lidos |
| 6 | **Agrupa por `classe` sem precisar**: gera 20 grupos em vez de 5, e o `$group` guarda mais estado em memória. | desempenho (e deixa o `_id` composto confuso) | `group nReturned=20` |
| 7 | `$project` no início **não economiza nada**: o otimizador já lê só os campos que o pipeline usa, então o `$project` só acrescenta um estágio. Aqui ele ainda causou o defeito 2. | desempenho | — |
| 8 | A saída sai com `_id` composto, **sem o campo `terminal`** pedido. | lógica / formato | — |

Curiosidade: o explain mostra que o otimizador trocou `$sort` e `$match` de lugar (`$limit > $match > $sort`). Isso é seguro, porque filtrar antes de ordenar dá o mesmo resultado. Mas ele **não pode** passar o `$match` por cima do `$limit` nem do `$group`, porque isso mudaria o resultado. Ou seja, o otimizador não corrige esses erros sozinho.

## c) Corrigido

```js
db.movimentacoes.aggregate([
  { $match: { classe: "Refrigerado" } },                                          // filtra primeiro (usa índice)
  { $group: { _id: "$terminal", kg_total: { $sum: "$peso_kg" }, mov: { $sum: 1 } } }, // com $ e só por terminal
  { $sort: { kg_total: -1 } },                                                    // ordena antes...
  { $limit: 3 },                                                                  // ...de limitar
  { $project: { _id: 0, terminal: "$_id", kg_total: 1, mov: 1 } }
])
```
| terminal | kg_total | mov |
|---|---|---|
| T2 | 322.311.912 | 20.091 |
| T1 | 322.205.360 | 20.047 |
| T3 | 320.367.289 | 19.959 |

**Provas de que está certo:**
- Somei "na mão" com `find({classe:"Refrigerado"})` e um laço no shell, sem aggregate: T2 322.311.912 / T1 322.205.360 / T3 320.367.289 / T4 319.591.169 / T5 318.285.468. Bate exatamente, e T4 e T5 ficam de fora do top 3.
- `mov` do T2 = **20.091**, o mesmo `n` do código de autenticidade (`LP-240734452-20091-40919`), que o gerador calculou com `classe: Refrigerado, terminal: T2`.
- Plano: `GROUP > FETCH > IXSCAN (idx_classe_ts)`, 100.016 chaves e 100.016 docs (antes eram 400.000), 5 grupos.

## d) Impacto em RAM, CPU e índices

No pipeline original, o filtro só aparece no fim, então o Mongo não tem como usar índice e lê os 400 mil documentos do disco/cache (COLLSCAN). Isso gasta I/O e CPU pra desserializar documento que vai ser descartado. Depois, o `$group` monta 20 grupos em memória em vez de 5. Aqui é pouco, mas o `$group` guarda estado pra cada chave distinta, e agrupar por campos a mais multiplica isso. Em coleções grandes ele pode estourar os 100 MB e precisar de `allowDiskUse`, o que deixa tudo mais lento. Já no pipeline corrigido, o `$match` no início usa o `idx_classe_ts`: ele lê só 1/4 dos documentos (100 mil), o `$group` recebe 4× menos dados e o `$sort` ordena só 5 linhas. A regra que tirei disso: **filtrar o mais cedo possível, agrupar só pelo necessário e ordenar antes de limitar.** A ordem dos estágios muda o resultado, não só a velocidade.
