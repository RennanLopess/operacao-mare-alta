# A4 — Covered query

```js
db.movimentacoes.createIndex({ tipo: 1, terminal: 1, container: 1 }, { name: "idx_tipo_terminal_container" })
db.movimentacoes.find({ tipo: "inspecao", terminal: "T2" }, { _id: 0, container: 1 })
```
Script: [a4.js](a4.js) · saída: [a4_saida.txt](a4_saida.txt) · explains: [coberta](a4_1_coberta_explain.json), [sem _id:0](a4_2_sem_id0_explain.json)

| | `{_id:0, container:1}` | `{container:1}` (sem `_id:0`) |
|---|---|---|
| stages | `PROJECTION_COVERED > IXSCAN` | `PROJECTION_SIMPLE > FETCH > IXSCAN` |
| totalKeysExamined | 15.992 | 15.992 |
| totalDocsExamined | **0** | **15.992** |
| nReturned | 15.992 | 15.992 |
| executionTimeMillis | 20 | 30 |

**Por que fica coberta:** o filtro usa `tipo` e `terminal`, e a projeção pede só `container`. Os três campos estão na chave do índice, então o Mongo monta a resposta direto da B-Tree (`PROJECTION_COVERED`) e nunca abre um documento: `totalDocsExamined: 0`.

**O que muda sem o `_id:0`:** o `_id` entra na projeção por padrão e **não está nesse índice**. Pra devolver o `_id`, o Mongo precisa buscar cada documento na coleção (estágio `FETCH`), e aí são 15.992 docs examinados, um por resultado. O IXSCAN continua igual, o que muda é o FETCH no meio. Aqui deu +10 ms, mas com a coleção maior que a RAM, cada FETCH pode virar leitura de disco, e aí a diferença cresce muito.
