# B1 — Agregação por terminal

```js
db.movimentacoes.aggregate([
  { $match: { classe: "Refrigerado", ts: { $gte: ISODate("2026-04-01T00:00:00Z") } } },
  { $group: { _id: "$terminal", total_mov: { $sum: 1 }, peso_total: { $sum: "$peso_kg" },
              peso_medio: { $avg: "$peso_kg" }, maior_peso: { $max: "$peso_kg" } } },
  { $sort: { peso_total: -1 } },
  { $limit: 3 },
  { $project: { _id: 0, terminal: "$_id", total_mov: 1, peso_total: 1, peso_medio: 1, maior_peso: 1 } }
])
```
Só usa os operadores permitidos (`$match` com `$gte`, `$group`, `$sum`, `$avg`, `$max`, `$sort`, `$limit`, `$project`).

## Índice para o `$match` inicial
```js
db.movimentacoes.createIndex({ classe: 1, ts: 1 }, { name: "idx_classe_ts" })
```
Igualdade em `classe` e depois o range em `ts`. O `idx_esr` da A1 não serve aqui porque começa por `terminal`, e o `$match` não filtra terminal.

## Prova: `db.movimentacoes.explain("executionStats").aggregate([...])`

O Mongo 8 empurrou o `$match` + `$group` pro engine SBE (o `$group` aparece dentro do `$cursor`). Árvore de execução real:

```
antes do índice                          depois do índice
project   nReturned=5                    project   nReturned=5
  group   nReturned=5                      group   nReturned=5
    project nReturned=69843                  project nReturned=69843
      filter nReturned=69843                   fetch  nReturned=69843
        scan  nReturned=400000                   ixseek nReturned=69843
```

| | antes | depois |
|---|---|---|
| plano | `GROUP > COLLSCAN` | `GROUP > FETCH > IXSCAN (idx_classe_ts)` |
| totalKeysExamined | 0 | 69.843 |
| totalDocsExamined | 400.000 | **69.843** |
| **docs que entraram no `$group`** | **69.843** | **69.843** |
| tempo (3 execuções, ms) | 136 / 131 / 132 | 159 / 106 / 97 |

O número que entra no `$group` não muda, porque o filtro é o mesmo. O que muda é quanto o Mongo precisa ler pra chegar nele: sem índice ele lê e descarta 330 mil docs (`scan 400000 → filter 69843`). Com índice ele lê só o que vai usar (`ixseek 69843 → fetch 69843`), ou seja, 1 doc lido por doc útil.

O ganho de tempo foi modesto (~130 → ~100 ms) porque o filtro pega 17% da coleção e tudo está em memória: o FETCH aleatório de 70 mil docs custa quase o mesmo que varrer 400 mil em sequência. Com a coleção maior que a RAM, ou com um filtro mais seletivo, a diferença cresce muito.
